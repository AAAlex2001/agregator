# Реферальная программа исполнителей

## Правила первого этапа

- Приглашающий и приглашённый — исполнители.
- Вознаграждение — 3 000 «плюсов» за нового коллегу.
- Общий фонд — 1 000 000 плюсов. В БД и API суммы — целые плюсы (`*_points`).
- Плюсы — внутренние баллы площадки, не деньги: нигде не называются рублями, не имеют
  рублёвого номинала, не обмениваются на деньги и не выводятся.
- Приглашённый подтверждает email и заполняет имя и хотя бы одну анкету направления.
- Телефон, проверка дипломов и платные действия не нужны.
- Один почтовый ящик участвует один раз, независимо от роли и повторной регистрации.
  Ящик определяется каноническим email: без регистра, без метки после «+», без точек в Gmail,
  с единым доменом и «.» = «-» в Яндексе. Так `ivan+1@gmail.com` и `i.van@gmail.com` — один участник.
- Плюсы используются на сайте; вывод не предусмотрен.
- При остатке менее 3 000 плюсов новые вознаграждения не начисляются. После 333 начислений останется 1 000 плюсов.

## Архитектура

Используем существующий модульный монолит FastAPI + SQLAlchemy + PostgreSQL.
Новые уровни абстракции, шина событий, очереди и дополнительные сервисы не требуются.

| Слой | Ответственность |
| --- | --- |
| routes/referral.py | HTTP-контракт; получение зависимостей и вызов use case |
| dependencies/referral.py | Сборка репозиториев, валидатора и use cases на одной DB-сессии |
| services/referrals/use_cases | Получение ссылки, привязка приглашения, начисление |
| services/referrals/validators.py | Роли, новый пользователь, запрет самоприглашения |
| services/referrals/emails.py | Канонический email почтового ящика |
| services/referrals/profile_policy.py | Явные правила заполненности анкет десяти направлений |
| services/referrals/repository.py | Только SQL и сохранение сущностей |
| services/referrals/bonus_repository.py | Бонусный счёт и журнал начислений |
| models, schemas | ORM-модели и типизированные DTO по шаблону проекта |

Use cases не создают соединения, не выполняют SQL и не коммитят транзакцию.
Валидация не изменяет данные. Репозитории не принимают бизнес-решения.
Границу транзакции, как и в остальном проекте, задаёт get_db.

## Данные

1. `referral_campaigns`: фиксированный фонд, размер вознаграждения, выданная сумма, признак активности.
2. `referrals`: пригласивший, приглашённый, канонический email, статус (enum `referralstatus`),
   даты регистрации и начисления.
3. `bonus_accounts`: баланс бонусов конкретного аккаунта.
4. `bonus_transactions`: журнал начислений со ссылкой на источник; одно начисление на приглашение.

Ссылка использует существующий Account.public_id. Генерация дополнительных кодов не нужна.
Первоначальный email приглашённого сохраняется в referrals. Удаление аккаунта не удаляет участие.
Журнал и бонусный счёт защищены внешними ключами от удаления вместе с аккаунтом.

## Сценарии

### Регистрация по ссылке

Роут регистрации после RegisterUserUseCase вызывает RegisterReferralUseCase в той же транзакции.
Регистрация от рефералки не зависит: недействительная ссылка, самоприглашение или уже
существующий пользователь не дают ошибку, аккаунт просто создаётся без приглашения.

1. Не исполнитель — без приглашения.
2. Для канонического email уже есть приглашение: PENDING переходит на новый аккаунт
   (повтор брошенной регистрации, в том числе без ссылки), пригласивший не меняется;
   завершённое участие повторно не используется.
3. Иначе по ссылке: пригласивший — активный исполнитель с подтверждённой почтой,
   это не тот же ящик, и у email нет других аккаунтов ни в одной роли.

Добавить пригласившего позже через API нельзя.

### Начисление

Роуты подтверждения email, личных данных и анкет направлений после основного use case
вызывают RewardReferralUseCase. Сервисы регистрации и направлений о рефералке не знают.
Если условия ещё не выполнены, приглашение остаётся PENDING.

1. Найти приглашение. Если его нет или результат уже окончательный — закончить.
2. Заблокировать строку фонда через SELECT FOR UPDATE.
3. Перечитать приглашение: другой запрос мог уже начислить бонус.
4. Проверить подтверждённый первоначальный email, роль, активность и заполненность профиля.
5. Проверить пригласившего и остаток фонда.
6. Создать или заблокировать бонусный счёт.
7. Изменить баланс, записать операцию, увеличить выданную сумму и поставить REWARDED.
8. Общий commit выполняет get_db. При ошибке откатываются все изменения.

Порядок блокировок одинаков: фонд, затем бонусный счёт. Для 333 вознаграждений одна блокировка
фонда проще и достаточна. Ограничения БД дополнительно запрещают отрицательный баланс,
выход за фонд и повторный источник операции.

### Статусы

- PENDING: ждёт выполнения условий или возобновления приостановленной программы.
- REWARDED: бонус начислен; повторная проверка ничего не меняет.
- POOL_EXHAUSTED: фонд закончился до выполнения условий.
- REJECTED: пригласивший удалён или больше не имеет права участвовать.

## API первого этапа

- `GET /api/referrals/me`: персональная ссылка, сумма вознаграждения, бонусный баланс,
  счётчики приглашений и остаток фонда. Доступен только активному исполнителю с подтверждённой почтой.
- `referral_code` в существующем multipart payload регистрации: публичный UUID пригласившего.
- Начисление автоматическое; публичного API для изменения баланса или привязки старого аккаунта нет.

Email и контакты приглашённых в кабинете не раскрываются.

## Фронтенд

Блок под «Вы — исполнитель» показывает ссылку, баланс и счётчики только исполнителю
с подтверждённой почтой. Использует общие Title, Subtitle, TextInput, Button и Skeleton.

- `entities/referral`: контракт API, запрос, форматирование сумм и хранение кода в текущей вкладке.
- `features/referrals/invite-colleague`: типизированный редьюсер загрузки, хуки загрузки
  и копирования, разметка панели.
- `widgets/referral-invitation`: связывает сессию с существующей модалкой регистрации.
- `/register?ref=UUID`: открывает модалку с ролью EXPERT; регистрацию можно открыть повторно.
- Существующий useRegister передаёт `referral_code` только в регистрации исполнителя.
  После успешной регистрации сохранённый код удаляется. При ошибке остаётся для повтора.

Передача кода сохраняется при переходах по сайту в этой же вкладке. Если браузер запрещает
sessionStorage, регистрация по прямой ссылке продолжает читать код из адреса.
При отказе Clipboard API поле выделяется для ручного копирования.

Проверки из папки frontend: `npx tsc --noEmit`, ESLint изменённых файлов, `npm run build`.
Проверки кода приглашения, склонения плюсов и редьюсера: `node --test test/referral.test.mjs` (Node 24).

## Граница с подписками

Первый этап включает приглашения, начисления и чтение бонусного счёта.
Покупка за бонусы должна быть отдельным use case существующего services/subscriptions.
Он сможет списать бонусы и активировать подписку в той же транзакции, с ключом повторного запроса.
Его нельзя помещать в referrals или подменять им оплату через YooKassa.

## Проверки

Unit-тесты: условия участия, самоприглашение, существующий пользователь, повтор регистрации,
все десять направлений, пустая анкета, подтверждение почты, повторное начисление, истощение фонда,
права доступа и ответ API.

Интеграционные тесты на отдельном PostgreSQL: конкурентные начисления одному приглашению,
борьба за последний бонус, откат транзакции, согласованность счёта/журнала/фонда,
сохранение участия при удалении и upgrade/downgrade миграции.
Нагрузочные тесты продакшена не запускаются. Проверки: Ruff lint, Ruff format и обычные unit-тесты.

## Ограничение защиты от накрутки

Подтверждение почты проверяет владение адресом, но не личность. Алиасы одного ящика сводятся
к каноническому email, но разные реальные ящики одного человека автоматически распознать нельзя
без дополнительной идентификации. Код не должен обещать такую защиту при выбранном условии
«достаточно подтверждённой почты».

## Запуск проверок

Из папки backend:

```powershell
python -m pytest test/unit -q
```

Для интеграционных тестов укажите отдельную PostgreSQL-базу с суффиксом `_test`:

```powershell
$env:REFERRAL_TEST_DATABASE_URL = 'postgresql+asyncpg://user:password@127.0.0.1:5432/referral_test'
$env:DATABASE_URL = $env:REFERRAL_TEST_DATABASE_URL
python -m pytest test/integration -q
```

Каждый тест создаёт собственную схему и удаляет только её. Без переменной
REFERRAL_TEST_DATABASE_URL интеграционные тесты пропускаются.

Перед запуском API на сервере необходимо применить миграции `174` и `175` обычным для проекта
способом (`alembic upgrade head`). 174 создаёт фонд, 175 переводит статус на enum,
176 переводит суммы из копеек в целые плюсы (фонд — 1 000 000 плюсов).
Расходование бонусов на подписки относится к следующему этапу.

# Архитектура frontend

Всё приложение находится в `src` и устроено по FSD. Новый код пишем так же, как
уже написанный рядом: все срезы одного слоя устроены одинаково (шаблон — в
`src/README.md`).

## Структура

- `src/app` — маршруты Next.js, layout, metadata, SEO, favicon и провайдеры приложения.
- `src/widgets` — композиция экранов и крупных блоков. Бизнес-запросы и редьюсеры
  принадлежат фичам и сущностям; состояние открытия UI может оставаться в виджете.
- `src/features/<действие>` — законченный пользовательский сценарий.
- `src/entities/<сущность>` — API, предметные типы, обработка данных и повторно
  используемые поля/карточки сущности.
- `src/shared` — общие UI, HTTP, технические функции и конфигурация.
- `src/shared/styles/colors.css` — единая палитра для последующей тёмной темы.

## Код

- Папки и обычные файлы называются `kebab-case`. Компонент находится в собственной
  папке: `index.tsx`, рядом `style.module.scss`, если нужны стили.
- API-функции находятся в `api`, типы и состояние — в `model`, разметка — в `ui`.
- Между модулями используем понятные публичные импорты. Внутри модуля — относительные.
- Не создавать `@x`, вложенный технический `shared` в сущностях и прокси-экспорты,
  скрывающие старые пути. Общая предметная модель должна иметь понятного владельца.
- Не использовать собственные generic-функции, `Partial`, `Pick`, `Omit`, `Record`,
  `useMemo`, `useCallback` и `any`. Стандартные типы React/Promise допустимы.
- Не удалять memo из существующего эффекта механически: сначала сохранить жизненный
  цикл подписки/запроса, исключить повторные подключения и циклическую загрузку.
- У функций короткие русские комментарии о назначении. Не описывать очевидные строки.
- Над предметным типом, интерфейсом или списком настроек писать один короткий русский
  JSDoc о назначении. Отдельные поля не комментировать: достаточно пояснения над типом.
- JSX-свойства, длинные импорты и объекты оформлять в несколько строк.
- Переиспользовать небольшие понятные компоненты: кнопка, поле, заголовок, подзаголовок.
  Не строить универсальную фабрику форм или динамический движок UI.
- Мультиселект без поиска. Сохранить текущие варианты и вид выбранных значений.
- Отмена HTTP-запроса добавляется только для существующего сценария отмены.

## Проверка и командная работа

- Перед изменением зафиксировать назначение модуля, его API и текущий внешний вид.
- После каждого созданного или изменённого файла прочитать итоговый код целиком:
  проверить одну ответственность, соответствие слою, понятные именованные обработчики
  и отсутствие дублированного состояния. Над типами и функциями оставлять один короткий
  комментарий о назначении; отдельные поля не комментировать.
- После изменения сверить результат с требованиями пользователя.
- Каждый агент редактирует согласованную область. Изменения границ/контрактов согласуются
  с координатором; после реализации другой агент проводит ревью.
- После завершения каждого модуля провести независимое ревью другим агентом и подходящие
  проверки его поведения, типов, кода и стилей до перехода к следующему модулю.
- Сохранить роли, права, multipart-поля, WebSocket, SEO, URL и состояния ошибок/загрузки.
- Проверить TypeScript, ESLint, `npm test` и production-сборку.
- Изменения стилей проверять в браузере. Не выдавать компиляцию за проверку внешнего вида.

# Frontend

Всё приложение находится в `src` и устроено по FSD.

## Где искать код

| Слой | Ответственность |
| --- | --- |
| `app` | Страницы Next.js, layout, SEO и провайдеры приложения. |
| `widgets` | Композиция крупных блоков из готовых фич и сущностей. |
| `features` | Законченные действия: войти, зарегистрироваться, изменить профиль. |
| `entities` | Данные предметной области: типы, API и переиспользуемая разметка. |
| `shared` | Общие UI-компоненты, HTTP и конфигурация приложения. |

Все срезы одного слоя устроены одинаково:

- сущность — `api/` (один запрос на файл), `model/` (`types.ts`, чистые функции,
  хуки загрузки, провайдер), `ui/`, `config/` для постоянных значений, `server.ts` для
  серверной загрузки, `index.ts`;
- фича — `model/` (типы, редьюсер формы, хук действия), `ui/`, `index.ts`;
- виджет — `ui/` и `index.ts`, без запросов и бизнес-логики.

Хук загрузки данных хранит одно состояние `{ данные, isLoading, error }` и флаг
`isActive` в эффекте; ошибка загрузки показывается на экране, тосты — только для
действий пользователя. Пустые фичи и виджеты заранее не создаём.

## Первый модуль: профиль проектировщика

```text
entities/design/
  api/
    get-design-profile.ts
    get-design-options.ts
    update-design-profile.ts
    upload-design-document.ts
    delete-design-document.ts
  config/registry.ts
  model/
    types.ts
    documents.ts
    provider.tsx
    profile-state.ts
    use-save-design-profile.ts
    use-upload-design-document.ts
    use-delete-design-document.ts
  ui/
    design-profile-fields/
    education-fields/
    qualification-fields/
    registry-fields/
  index.ts

features/edit-design-profile/
  model/
    use-design-profile-form.ts
  ui/
    design-profile-form/
    design-documents/
    document-group/
  index.ts

widgets/design-profile/
  ui/design-profile-editor/
  index.ts
```

`DesignProfileFields` показывает поля и передаёт изменения наружу. Его можно
использовать при регистрации и в настройках профиля. Запросы из него не выполняются.

`DesignProfileEditor` загружает анкету и справочники хуком сущности
`useLoadDesignProfile`, показывает заглушку или ошибку и собирает провайдер
сущности с формой редактирования. При смене пользователя страница настроек
перемонтирует редакторы с `key={user.id}`.

`DesignProfileProvider` хранит сохранённую анкету и состояние запросов. Хуки сущности
выполняют запросы и передают результат редьюсеру. Редьюсер только обновляет состояние.

`DesignProfileForm` хранит черновик полей и вызывает операции сущности.
Ответ загрузки файла не стирает введённые данные. Документы сохраняются сразу,
поля — по нажатию «Сохранить анкету».

## Авторизация

`entities/user` выполняет запросы и хранит текущий аккаунт. Фичи `login`,
`switch-role` и `confirm-email` управляют полями и последовательностью действий.
Переход на другую страницу задаёт внешний экран через callback.

В переключении роли `useAvailableRoles` загружает список, `useSwitchAccountRole`
подтверждает пароль и обновляет сессию, а `useSwitchRole` управляет формой.
При ошибке загрузки профиля повторяется только GET: пароль второй раз не отправляется.

При подключении `RoleSwitcher` нужно сохранить его смонтированным во время смены
аккаунта: не помещать под `key={role}` или в исчезающую ветку `user !== null`.
Оболочка должна показывать ошибку профиля и действие повторной загрузки, в том числе
после закрытия окна переключения. Эта интеграция ещё не подключена к страницам.

Форма подтверждения почты получает `key` из адреса и роли. Подтверждённый аккаунт
относится к конкретной форме и сохраняется при повторной загрузке её профиля.

## Соглашения

- Папки и обычные файлы — `kebab-case`; компоненты — `PascalCase`.
- Каждый UI-компонент — папка с `index.tsx` и соседним `style.module.scss`.
- Между модулями используем публичный `index.ts`: `@/entities/design`.
- Общие компоненты импортируем напрямую: `@/shared/ui/button`.
- Внутри одного модуля используем относительные импорты.
- `@/` указывает на `src`.
- Фичи не импортируют другие фичи. Их соединяет виджет или страница.
- Сущность не импортирует другую сущность, фичу или виджет.
- Виджет собирает интерфейс; бизнес-состояние и редьюсеры живут в фичах и сущностях.
- В `shared` нет типов направлений, бизнес-правил и ссылок на отраслевые реестры.
- У функций — короткий русский комментарий о назначении или важном поведении.
- Над типом, интерфейсом и списком настроек — один короткий комментарий о назначении.
  Отдельные поля не комментируем.
- JSX с несколькими свойствами пишем в несколько строк. Длинные импорты и объекты
  тоже разбиваем на строки.
- Не используем `useMemo`, `useCallback`, `any` и универсальные обёртки без задачи.
- Прикладные типы описываем явно, без `Partial`, `Pick`, `Omit`, `Record` и
  собственных параметров типа `<T>`. Поля получают обработчики с конкретными
  аргументами: строкой, числом, флагом или массивом.
- Стандартные типы библиотек (`Promise`, свойства HTML-компонентов React)
  используем с конкретным типом результата или элемента.
- Поля API сохраняют серверные названия: дополнительное преобразование имён не нужно.
- Множественный выбор — компактный выпадающий список без поиска.

ESLint проверяет перенос JSX-свойств и запрещает `useMemo` и `useCallback`.

Структура следует понятному разделению из Amler-Prod: сущность предоставляет
данные и запросы, фича управляет действием, виджет собирает интерфейс.
Папки компонентов и короткие комментарии — как в `kupec/frontend/src`.

## Проверка

Из каталога `frontend`:

```sh
node node_modules/typescript/bin/tsc --noEmit --incremental false
node node_modules/eslint/bin/eslint.js src
node --test "src/**/*.test.mjs"
```

Для запуска TypeScript-тестов без дополнительных зависимостей нужен Node.js 24.

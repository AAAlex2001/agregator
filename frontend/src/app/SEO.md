## Динамические страницы

| Страница | Метаданные и серверное содержимое |
| --- | --- |
| `/news/[slug]`, `/blog/[slug]` | `generateMetadata` загружает статью на сервере и проверяет её `kind`. Заголовок: `meta_title || title`; описание: `meta_description || excerpt || title`; keywords: `meta_keywords || tags`. Canonical использует slug ответа API. Open Graph содержит тип article, даты публикации/изменения, tags и обложку с fallback. Отсутствие/неверный kind даёт noindex и `notFound()` страницы. |
| `/rtn/[slug]` | Аналогичные fallback заголовка/описания/keywords, canonical по slug ответа, даты, tags и `/og-default.png`. Отсутствие даёт noindex и `notFound()`. |
| `/posts/[id]` | Только положительный безопасный integer. Нет поста — `notFound()`. Неопубликованный пост: noindex/nofollow. Опубликованный оригинал: index/follow. Репост: noindex/follow. Сохранить собственный canonical `/posts/{id}`, title/description от API, cover fallback и даты. |
| `/order/[uuid]` | Серверная загрузка для метаданных; описание собирается из комментария, заказчика, цены, срока и требований. При ошибке — «Заявка не найдена», noindex/nofollow и fallback images. Успешная карточка использует Twitter `summary`, как в исходнике. Сам preview в исходнике загружается на клиенте; это не доказательство SSR текста заказа. |
| `/labor/listing/[public_id]` | Заголовок/описание из прежних `laborShareTitle` и `laborShareDescription`, canonical по public_id, OG website, Twitter summary_large_image. Содержимое заявки приходит на сервере. |

Данные статей, РТН и их списков должны оставаться в серверной разметке,
включая контент, ссылки на соседние страницы и соответствующий JSON-LD.
Не заменять серверную загрузку пустым экраном с `useEffect`.

Серверные загрузчики публикаций передают `session_id` в API, чтобы автор видел
свой черновик и личные отметки. Они используют `cache: "no-store"`.
Дедупликация в пределах серверного рендера не должна превращаться в общий кеш
между пользователями. Это относится и к метаданным доступного автору черновика.

## Пагинация и canonical

- `/news?page=N`: исходник загружает отдельную страницу по 24 записи,
  передаёт обычный href следующей страницы, canonical остаётся `/news`.
- `/blog?page=N`: исходник загружает записи с первой страницы по N включительно,
  по 12 записей, максимум четыре связанные страницы; canonical остаётся `/blog`.
- `/rtn?page=N` без фильтров: по 12 записей с начала до страницы N,
  максимум десять связанных страниц. Страница 1 canonical `/rtn`, последующие
  `/rtn?page=N`, в title добавляется номер страницы.
- `/rtn` с поиском/фильтрами: noindex/follow, включая googleBot.
  Сохранить проверку через прежний `toCatalogQuery`, а не закрывать любую
  страницу с query string: обычная пагинация индексируется.
- `/posts?page=N`: сервер отдаёт записи с первой страницы по N, canonical
  указывает на первую страницу ленты. Для `?author=ID` canonical сохраняет
  автора, но убирает номер страницы. Ссылки «Показать ещё» остаются обычными href.

Разные правила выше уже существуют в проекте. При рефакторинге не приводить
их к одной схеме без отдельного решения об изменении SEO.

## robots.txt

Сохранить `dynamic = "force-static"`, один userAgent `*`, существующие списки
и `${SITE_URL}/sitemap.xml`.

Disallow: `/admin`, `/api`, `/chat`, `/customer`, `/expert`, `/order`,
`/responses`, `/settings`, `/landing`, `/archive`, `/notifications`, `/support`.

Allow: `/`, `/orders`, `/reviews`, `/news`, `/posts`, `/blog`, `/rtn`,
`/rtn/ask`, `/zepb-registry`, `/expert-contacts`,
`/training/defectoscopist-certification`, `/requisites`, `/offer`,

У `/order/[uuid]` уже есть метаданные для превью ссылки при запрете `/order`
в robots. Это существующий контракт; не менять его вместе с архитектурой.

## sitemap.xml

Исходник: `frontend/app/sitemap.ts`. Сохранить `dynamic = "force-dynamic"`,
`revalidate = 300`, публичный SITE_URL, порядок и ошибки независимых источников.
Ошибка одного источника возвращает для него пустой список, не удаляет остальные.

Статические записи: `/`, `/orders`, `/posts`, `/news`, `/blog`, `/rtn`,
`/rtn/ask`, `/nir`, `/sudebnaya-ekspertiza`, `/kadastrovye-raboty`, `/audit-supb`,
`/ekspertiza-promyshlennoy-bezopasnosti`, `/tehnicheskoe-diagnostirovanie`,
`/proektirovanie`, `/ekologiya`, `/inzhenernye-izyskaniya`, `/reviews`,
`/zepb-registry`, `/expert-contacts`, `/training/defectoscopist-certification`,
`/requisites`, `/offer`, `/user-agreement`, `/privacy-policy`.

Динамические записи:

- Новости и блог: все slug из article sitemap, `lastModified = updated_at`,
  weekly, priority 0.8. Для новостей также страницы 2..ceil(count / 24),
  daily, priority 0.6. Страницы пагинации блога исходник сюда не добавляет.
- РТН: загрузить все страницы по 12 до `has_more = false`; добавить все slug
  (monthly, priority 0.7, `published_at` или текущая дата), а также страницы
  каталога 2..min(10, ceil(count / 12)), daily, priority 0.6.
- Публикации: только опубликованные оригиналы из posts sitemap, weekly,
  priority 0.7, `updated_at`; уникальные `/posts?author=ID`, daily, priority 0.5.
  API sitemap публикаций имеет серверный `revalidate: 300`.
- Закрытые страницы кабинета, черновики и репосты не добавляются.

Priority/changeFrequency статических маршрутов сверять с исходным массивом,
а не заменять одним значением для всех URL. `/personal-data-consent` в исходном
статическом sitemap отсутствует; изменение состава — отдельное решение.

## Проверка перед переключением

1. Для каждой перенесённой страницы сравнить metadata/canonical/robots, включая
   наследование от layout. Сохранить исходные href публичных и кабинетных версий.
2. Проверить серверный ответ без сессии для списков и деталей: title, description,
   canonical, robots, основной текст, ссылки пагинации, валидный JSON-LD.
3. Проверить пустой/ошибочный slug или id, черновик, оригинал и репост, поисковые
   фильтры РТН, вторые страницы списков, ссылку с ref и приватный маршрут.
4. Проверить кабинет с сессией: noindex сохранился, переходы публичная страница
   → `/landing/**` не меняют canonical публичных страниц для гостя.
5. Сравнить robots.txt и sitemap.xml на одинаковых данных API; отдельно проверить
   частичный отказ API и отсутствие приватных URL в sitemap.
6. Проверить public assets, production-сборку и HTML уже активного `src/app`.
   Пока существует активный корневой `app`, его успешный запуск не доказывает
   готовность новых маршрутов.
